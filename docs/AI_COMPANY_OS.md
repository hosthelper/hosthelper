## 0. 출처와 가정

**출처**: 외부 가이드 *AI COMPANY OS v1.0 — AI 직원 7명으로 회사를 세팅하는 법* (NOMAD MARGIN, 9p). 핵심 주장 5가지를 헬퍼유니버스 맥락으로 번역한 것이 이 문서입니다.

| 원문 단계 | 핵심 주장 |
|---|---|
| 1. DIRECTION | AI 직원보다 먼저 **회사 목표 1개**. 끝났는지 확인 가능한 숫자여야 한다 |
| 2. TEAM MAP | 직원처럼 보이게 하는 게 목적이 아니다. **입력 → 고정된 결과물**을 정하는 게 목적 |
| 3. COPY & RUN | 부서별 프롬프트는 `[입력] / [업무] / [출력] / [규칙]` 골격 |
| 4. WORKFLOW | 자동화의 핵심은 도구 수가 아니라 **인수인계**. 앞 팀 결과물이 다음 팀 입력이 된다 |
| 5. DAY ONE | 전 부서를 완성하지 마라. 오늘은 **목표 1개 · 부서 3개 · 결과물 1개** |

원문 9페이지는 저자 본인의 전자책·칼럼 판매 퍼널이므로 반영하지 않았습니다.

**명시적 가정 2가지** — 실제와 다르면 이 절부터 고쳐 주세요.

1. **비전과 30일 목표를 분리했습니다.** 대표가 제시한 목표는 *"회원에게 헬퍼유니버스 사업을 인지·가입·결제까지 완벽한 퍼널로 만들어 글로벌 기업으로 키운다"* 입니다. 이는 12개월 비전이지 원문이 요구하는 "30일 안에 끝났는지 확인 가능한 숫자"가 아닙니다. 그래서 §1에서 **비전 1문장 + 30일 북극성 숫자 1개 + 선행지표 3개**로 나눴습니다.
2. **확인되지 않은 브랜드는 비워 뒀습니다.** 헬퍼아카데미·라이프헬퍼·넥스트헬퍼·BGN은 이 저장소와 스킬 어디에도 정의가 없습니다. 추측해서 채우지 않고 `TBD`로 두었으며, 채우는 절차는 [`00-brand-intake.md`](prompts/company-os/00-brand-intake.md)에 있습니다.

## 4. 인수인계 흐름

원문의 핵심: *"자동화의 핵심은 도구 수가 아니라 인수인계입니다. 앞 팀의 결과물이 다음 팀의 입력이 되면 회사가 끊기지 않고 돌아갑니다."*

**전달 규칙: 요약하지 말고 앞 팀이 만든 결과물을 그대로 전달합니다.** 요약하는 순간 다음 팀이 판단 근거를 잃습니다.

| 단계 | 담당 | 앞 팀 결과물 (= 이 팀 입력) | 이 팀 출력 | 완료 조건 |
|---|---|---|---|---|
| 01 기획 | 대표실 | §1 목표 + §2 브랜드 지도 | 우선순위 5개 · 부서별 첫 업무 | 부서마다 "첫 업무 1개 + 완료 조건"이 문장으로 적혔다 |
| 02 제작 | 마케팅 · 개발 | 대표실 우선순위 원문 | 주제 3개 / 최소 버전 기능 목록 | 오늘 발행 가능한 주제 3개, 또는 배포 가능한 기능 1개 |
| 03 판매 | 영업 | 마케팅 주제·근거 원문 | 첫 DM · 후속 · 상담 질문 | 상담 예약 요청까지 이어지는 대화 1세트가 있다 |
| 04 응대 | 고객지원 | 영업이 받은 실제 질문 원문 | FAQ 10 · 개선 요청 | 사람이 결정할 항목(환불·법률·개인정보)이 따로 표시됐다 |
| 05 자동화 | 운영 | 04까지 수동으로 1회 성공한 기록 | 자동화 흐름 · 실패 알림 문구 | 실패했을 때 누구에게 무엇이 통보되는지 적혔다 |
| 06 확장 | 대표실 · 재무 | 01~05 결과물 + 현금표 | 유지 / 중단 / 확대 결정 | 각 항목에 대해 셋 중 하나가 선택됐다 |

## 5. 자동화 원칙과 현황

**순서를 지킵니다.** 수동으로 한 번 성공 → 반복되는 부분 확인 → **그 부분만** 자동화 → 실패 알림 추가. 성공한 적 없는 일을 자동화하면 실패를 빠르게 반복할 뿐입니다.

### 이미 자동화된 것

| 워크플로 | 트리거 | 하는 일 |
|---|---|---|
| `.github/workflows/build-reel-daily.yml` | `apps/changup-site/reel/daily/manifest.json` push (main) | 유니 보이스오버 + 카드뉴스 6장 → 릴스 MP4 합성·커밋 |
| `.github/workflows/build-reel.yml` | 워크플로 파일 자체 push | 카드뉴스 릴스 합성 (무한루프 방지용 트리거 한정) |
| `.github/workflows/build-reel-campaign.yml` | 워크플로 파일 자체 push | 양도인·양수인 캠페인 릴스 2편 합성 |
| `.github/workflows/publish-reel.yml` | `reel_<prefix>.mp4` push (main) | 인스타 릴스·유튜브 쇼츠·스레드 자동 게시. 토큰 없으면 조용히 건너뜀 |
| `.github/workflows/ci.yml` | push (main, `claude/**`), PR | 빌드·테스트 |

### 자동화가 아닌 것 (수동)

- `.github/workflows/changup-content.yml` — **수동 전용·폐기 예정**입니다. 스케줄이 제거되어 `workflow_dispatch`로만 동작합니다. 기사 발행은 현재 Claude 데일리 루틴이 직접 작성합니다.
  > `apps/changup-site/README.md` §콘텐츠 발행에는 아직 "자동(권장) 5시간"으로 적혀 있어 **워크플로 실제 상태와 어긋납니다.** 개발팀 백로그 항목입니다.
- 4채널 발행 — mirra에 **초안(draft)** 으로 올라가고 사람이 검토 후 발행 (`uni` 스킬 §6).
- 리드 후속 연락, 상담 예약, 정산 확인.

### 실패 알림

자동화에는 반드시 실패 알림이 붙어야 합니다. `publish-reel.yml`은 `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`가 있으면 결과를 통보합니다. 새 자동화를 만들 때 [`07-operations.md`](prompts/company-os/07-operations.md)가 실패 알림 문구를 함께 만들도록 되어 있습니다.

## 6. 첫날 60분 체크표

원문 기준: *"AI 직원 7명을 모두 돌리는 것이 아니라, 부서 하나가 실제 결과물 하나를 끝내는 것."*

|---|---|---|
| 00–10 | 회사 목표 1개 적기 | §1의 빈칸 4개(북극성 숫자, 선행지표 3개)를 채운다 |

## 7. 가드레일

모든 부서 프롬프트에 공통 적용됩니다. 위반하면 결과물을 폐기합니다.

**사실성**
- 확인되지 않은 수치·후기·사례를 만들지 않습니다. 모르면 `확인 불가`로 표시합니다.
- 존재가 확인되지 않은 브랜드·계정·매물을 서술하지 않습니다 (§2의 `TBD` 4건 포함).

**법적 안전장치** (`uni` 스킬 §2)
- 수익·법률 단정 금지. 권리금·전대·외국인관광도시민박업 요건 등은 "확인이 필요하다"를 붙입니다.
- 자기지칭 "중개" 워딩을 쓰지 않습니다 (공인중개사법 방어). 공실헬퍼는 **공인중개사 연결**입니다.
- 환불·법률·개인정보 판단은 AI가 결정하지 않고 사람 결정 항목으로 분리 표시합니다.

**표현**
- 이모지 금지. 강조는 `·` `—` 등 텍스트 기호로.
- 운영·사업·UI 텍스트는 한국어 우선 (`CLAUDE.md` §7).

**보안** (`CLAUDE.md` §3)
- 사업자등록번호·API 키·개인 연락처를 프롬프트 본문에 넣지 않습니다. 필요하면 `docs/BUSINESS_ENTITY.md`를 참조하라고만 씁니다.
- 시스템 프롬프트에 `Date.now()`·세션 ID 등 가변값을 넣지 않습니다 (프롬프트 캐시 파괴).

## 8. 이 문서를 코드로 옮길 때

지금은 문서와 복붙 프롬프트만 있습니다. 반복 실행이 확인된 부서부터 `packages/ai/src/company/<dept>.ts`로 옮깁니다. 그때 지켜야 할 것:

- `@hosthelper/ai`를 반드시 경유합니다. API 모듈에서 `@anthropic-ai/sdk`를 직접 부르지 않습니다.
- 각 프롬프트의 `[출력]` 절은 **필드 목록**으로 적혀 있으므로 zod 스키마로 그대로 번역됩니다. 기존 예시: `packages/ai/src/dispute.ts`의 `DisputeOutputSchema`.
- 시스템 프롬프트에 `cache_control: { type: "ephemeral" }`, 비자명한 추론에 `thinking: { type: "adaptive" }`.
- 호출 전 `TokenBudget.check()`, 호출 후 `record()`. 결과는 `LLMCall`에 기록하고 운영상 중요한 판단은 `Decision`에 남깁니다.

세부 규칙은 루트 `CLAUDE.md` §3을 따릅니다.
