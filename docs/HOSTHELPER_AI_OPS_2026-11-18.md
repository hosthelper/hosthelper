## 아키텍처

1. 승인된 예약 API 또는 기존 구글장부 스냅샷을 예약 매핑 수집기로 수집한다. 원본 확인시각을 보존한다.
2. 예약코드, 숙소, 객실, 체크인/체크아웃, 변경/취소를 중복 제거하고 내부 청소 작업 큐를 생성한다.
3. 청소자 모바일 웹앱은 로그인/권한으로 담당 객실만 노출하고, 청소시작/완료/사진2장 이상/비품 부족/특이사항을 수집한다.
4. Slack은 내부 배정, 검수/이상 알림, 구매 승인, 일일 보고의 중심이다. 비밀번호 및 손님 개인정보는 남기지 않는다.
5. Claude는 판단 보조, 다국어 FAQ/게스트 응답 초안 및 특이사항 분류를 담당한다. AI는 직접 결제하거나 예약을 변경하지 않는다.
6. Pickle은 사용자가 허용한 서비스 범위에서만 실행한다. Slack을 통한 Pickle-클로드 직접 통신 가능 여부는 공식 API, 앱 권한, 실제 메시지/호출 테스트가 필요하다.
7. 외부 API 실행기는 조건/권한/중복 여부를 재검증한 뒤 메시지를 발송하거나 승인된 구매를 수행한다.

## 청소 완료 후 얼리체크인 조건

- 예약상태 confirmed, 객실 매핑 검증, 같은 객실 충돌 없음
- 외부 OTA/PMS에서 15분 이내 확인 또는 운영자의 공식 원본 수동 검증
- 예약 체크인 당일(Asia/Seoul)
- 청소 완료 및 애프터 사진 최소 2장 + 검수 승인 + 미해결 이슈 없음
- 사전 승인한 얼리체크인 정책 적용
- 동일 예약에 대한 중복발송 없음
- 공식 메시지 채널의 호출 권한 확인
- AI 로직은 발송 요청만 생성. 별도의 승인된 서버 실행기에서 반드시 원본 재검증 후 발송
- 출입 코드 전달은 별도의 보안 승인 플로우이며 Slack, AI 프롬프트, 일반 로그에 저장하지 않는다

## 구매/정산

청소팀 부족 재고 실사 → 최근 영수증/주문 번호 및 상품 SKU 대조 → 중복 주문 검증 → 운영자 승인 → 실제 구매 → 영수증/비용 정산. 1차 버전에서 승인 없이 구매 결제하지 않는다. 예약은 97% 공동호스트/3% 대표호스트 분배를 원장에 구분하고, 위탁 운영수수료는 계약별 정산 기준과 실입금을 대조한다.

## API 설계(미구현)

- POST /api/ops/agent/events : 권한/서명 체크 및 dedupe
- GET /api/ops/cleaning/today : 청소자별 담당 객실 조회
- POST /api/ops/cleaning/:id/report : 사진/체크리스트/재고/특이사항 제출
- POST /api/ops/cleaning/:id/inspect : 담당자 검수
- POST /api/ops/agent/actions/:id/approve : 운영자 승인
- POST /api/ops/agent/actions/:id/execute : 서버 실행기만 실행
- GET /api/ops/agent/audit : 중복/오류/재시도/승인 기록

2. 청소 모바일 작업/사진/검수/Slack 내부 메시지 1건 E2E.

4. 공식 OTA/PMS 메시지 기능 승인 후 답변 초안 → 검수 → 안전 발송 1건 E2E.
5. 비품 발주 승인 및 증빙 대조, 점주별 정산/월별보고 검증.
6. 출입 비밀번호/환불/취소는 높은 권한·감사기록 후 별도 검증.
